# ADR 0002: Semantic flow graph is the canonical call-flow model

**Status:** accepted
**Date:** 2026-10-23

## Context

The alpha console stores a graph whose nodes are raw FreeSWITCH applications
(`answer`, `playback`, `transfer`, `hangup`) and whose compiler topologically
sorts a linear chain. That was the right first step: it proved the Vue Flow
canvas, the Frappe document model and the XML-curl path.

It is not the product model.

A world-class call-flow editor needs to express:

- a digit menu with one branch per digit plus timeout handling;
- a time-of-day or holiday condition with match/no-match branches;
- a ring group or queue followed by a fallback;
- loops such as "invalid digit, replay the menu";
- reusable semantic steps that compile to more than one FreeSWITCH action;
- validation before the flow reaches FreeSWITCH.

A linear list of raw applications cannot represent those intents without
leaking FreeSWITCH mechanics back into the UI.

## Decision

1. **The canonical stored model is a semantic flow graph, schema v1.** It is
   stored as JSON in `FS Dialplan.graph` with
   `graph_format = "semantic"`.
2. **Nodes are intent-level.** The first palette is:
   `answer`, `play`, `menu`, `time`, `ring_group`, `queue`, `voicemail`,
   `transfer`, `conference`, `park`, `set`, `sleep`, `record` and `hangup`.
3. **Edges carry a source handle.** Handles are `next`, `digit:<digit>`,
   `timeout`, `match` and `no_match` as appropriate for the node type. This is
   the model that Vue Flow ports will bind to.
4. **A node registry owns the contract.** Each node type declares its outputs,
   required data, defaults and compiler. The compiler is server-side Python; the
   browser sends intent, never XML.
5. **Compilation is a state machine.** Each semantic node compiles to a named
   FreeSWITCH extension. The entry extension matches the real destination and
   transfers to the entry node. Every edge compiles to a transfer to the target
   node extension. Branch nodes transfer to a selector; each branch is a small
   selector extension that re-checks the dispatch destination and its own branch
   condition. Extension scanning provides the fallthrough, so the compiler does
   not depend on nested-condition break behavior.
6. **The generated extension names are deterministic:**
   `fs_flow_<flow>_entry` and `fs_flow_<flow>_<node>`. This makes the XML
   readable, diffable and testable. A later publishing feature can compare two
   compiled versions without guessing which extension represents which node.
7. **Validation is strict.** Unknown types, missing required data, duplicate
   node or edge IDs, unknown handles, duplicate handles, missing outputs,
   unreachable nodes and outgoing edges from terminal nodes are rejected before
   compilation.
8. **Raw graphs remain supported.** Existing `graph_format = "raw"` documents
   compile through the original linear compiler. The raw format is the advanced
   escape hatch and the migration path; it is not the primary editor.
9. **XML is an output.** The XML tab is generated by the same compiler
   FreeSWITCH uses. The browser never edits the compiled XML as the source of
   truth.

## Why a state machine instead of nested XML for the whole graph

A branching graph can be lowered in two ways:

- **Inline path expansion:** duplicate downstream actions into every branch.
  This is simple for tiny flows but explodes combinatorially and makes shared
  joins impossible to maintain.
- **Named extensions plus transfers:** each node is a small extension and each
  edge is a transfer. This supports branches, joins and intentional loops
  without duplicating the downstream graph.

FS Switch chooses the second form. The trade-offs are accepted:

- More extensions are generated than a hand-written dialplan would use.
- Debugging requires looking up deterministic extension names, which the console
  can show next to each node.
- `transfer` re-enters the dialplan; channel variables must be preserved
  deliberately. The compiler uses `set` for flow state and `transfer` for node
  transitions, and tests must verify variable-dependent branches in a real
  FreeSWITCH lab.

## Consequences

### Positive

- The UI can expose IVR menus, time routing, queues and ring groups without
  exposing FreeSWITCH application syntax.
- Branching flows compile without path explosion.
- Validation catches broken routes at save time.
- The generated XML is deterministic and testable.
- The node registry is the extension point for LCR, media, TTS, ASR and AI
  nodes later.

### Negative / risks

- A semantic flow is not a one-to-one representation of the final XML. The
  console must show the generated XML and the extension name for each node.
- `transfer`-based transitions need careful lab testing for channel-variable
  persistence, caller ID and queue/agent context.
- A generic catch-all dialplan extension with a lower priority can intercept a
  synthetic `fs_flow_...` destination. Semantic flow extensions must be emitted
  before catch-alls, and this must be checked by the route/publish validator.
- Strict validation can feel rigid. The UI should explain missing ports rather
  than only returning a backend error.

## Migration

- Existing documents keep `graph_format = "raw"` and compile exactly as before.
- New semantic documents use `graph_format = "semantic"`.
- The frontend can initially expose a format selector and the semantic JSON
  preview, then replace the node palette and property drawers in the next
  milestone.
- The raw compiler and semantic compiler share `compile_extension` as the
  adapter, so `compile_dialplan`, XML-curl and the preview endpoint do not need
  separate branches.

## Test strategy

- Unit-test every node's generated action or branch.
- Golden-test complete XML for a linear flow and a menu with timeout.
- Validate unknown handles, missing outputs, unreachable nodes and terminal
  edges.
- Test XML escaping for prompts and data values.
- Add a real FreeSWITCH lab test for menu selection, timeout, loop and queue
  transfer before publishing the semantic editor as a supported feature.
